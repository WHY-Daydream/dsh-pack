## 背景：为什么是 peer range 问题，而不是代码问题

最新 DSH（npm `next` 0.1.2-rc.1 / GitHub 源码 0.1.3-alpha.1）的接口面与 dsh-pack 消费的 API 完全兼容：

`loadProfile` / `loadOptionalPatches` / `composeEntries` / `PROFILE_PATCH_FILENAME`（@deepseek-ai/dsh-app-boot）、
`resolveDshHome`（@deepseek-ai/dsh-home-paths）、`CommandInvocation` / `CommandResult`（@deepseek-ai/dsh-commands）、
`PatchOptions`（@deepseek-ai/cordis-plugin-include）、Cordis `Context` —— 均无破坏性变化。

真正的阻塞是 npm semver 对 prerelease 的匹配规则：**候选 prerelease 只有与 range 内某比较器共享
major.minor.patch 元组时才被允许匹配**。因此：

| range 写法 | `0.1.2-rc.1` | `0.1.3-alpha.1` | `0.2.0` |
|---|---|---|---|
| 旧 `>=0.1.0-rc.5` | ❌（ERESOLVE） | ❌ | ✅（反而放行！） |
| 单窗口 `>=0.1.0-rc.5 <0.2.0-0` | ❌（ERESOLVE） | ❌ | ✅→❌（上界生效但 prerelease 仍被挡） |
| **v0.6.1 union**（见下） | ✅ | ✅ | ❌ |

一个 range 无法表达"所有未来 0.1.x prerelease"，必须对每条已发布 / 源码内 prerelease 行显式加
`>=X-0 <0.2.0-0` union 成员。**禁止再"简化"回单 range**——`tests/peer-range.spec.ts` 是防回归契约。

## v0.6.1 peer range（最终）

```text
>=0.1.0-rc.5 <0.2.0-0 || >=0.1.1-0 <0.2.0-0 || >=0.1.2-0 <0.2.0-0 || >=0.1.3-0 <0.2.0-0
```

覆盖行（**tested with current DSH 0.1.x prerelease lines**——已测线清单，非"未来全量"承诺）：
0.1.0（rc.5 起）· 0.1.1（npm 已发布 rc.1/rc.2）· 0.1.2（npm alpha/rc）· 0.1.3（源码 alpha.1）+ 任意 0.1.x stable。
语义：**与当前 DSH 0.1.x 线验证兼容；0.2.x 不自动放开**。DSH 发布新的 0.1.x prerelease 行时，
须按本条目规则补 `>=X-0 <0.2.0-0` union 成员并过 regression 后再发版；放开 0.2.x 前必须先跑 compatibility matrix。
